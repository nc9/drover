---
title: Untrusted data
description: Fence text an outsider controls so it reaches the model as data, not instructions.
---

Any agent that reads outside text (web pages, emails, tickets, tool results that
quote them) can be told what to do by that text. drover ships a **fence**: a
tagged block with a per-run random nonce, plus cleaning that stops a value from
closing or opening a tag. The model is told once, in the system prompt, that
everything inside a fence is data whatever it claims.

```ts
import { createFence, defineAgent } from "@droveragent/core";
import { untrustedResultsPlugin } from "@droveragent/plugins";

const fence = createFence(); // one per run: the nonce is random

const spec = defineAgent({
  id: "page-reader",
  systemPrompt: `You summarise pages.\n\n${fence.note()}`,
  // ...
  tools: ["fetch_page"],
});

runAgent(spec, input, {
  plugins: [untrustedResultsPlugin({ fence, tools: ["fetch_page"] })],
});
```

A tool that builds its own output can call `fence.wrap("page", value)` and be
listed in `selfFenced`, so it is not wrapped twice.

## Fail closed: untrusted unless positively marked trusted

The invariant: **anything a tool returns is untrusted unless it is positively
marked trusted; the mark is stored with the data it describes.** Every
bookkeeping miss (an id never recorded, a mark dropped at run end, a restart, a
resumed run) over-fences; none can under-fence.

- Results of the listed tools are always wrapped, errors and defects included
  (an upstream error can echo a page title). The plugin never looks at what the
  output looks like: a result that contains something fence-shaped is wrapped like
  any other. The only way out of wrapping is the explicit `selfFenced` list, and
  those tools still count as untrusted for the rule below.
- Every other tool call is marked trusted (by run and tool-use id). A reader tool
  (a stored or derived copy by id: `show_tool_result` by default, `readers` to add
  others) returns its output fenced unless the id it was asked for is marked
  trusted. An id the plugin never saw, or one whose mark was cleared, is fenced.
- The mark lives in the plugin, per run, and is cleared at run end. Data that
  outlives it (a truncate store shared across runs, a resumed run) reads back
  fenced; the cost of that is over-fencing trusted data, never leaking untrusted.
- Put `untrustedResultsPlugin` **after** `truncatePlugin` so the truncated head
  and its marker are fenced too. A tool of your own that returns a derived copy of
  an untrusted result must be added to `readers`.

## What the fence does to text

| Input | Result |
|---|---|
| `</untrusted-data-NONCE>` in the text | `<` and `>` escaped as `<` / `>`; the block cannot be closed |
| the nonce itself in the text | replaced by `[nonce]` |
| fullwidth brackets (`＜`) | NFKC turns them into ASCII first, then escaped |
| guillemets, math and CJK brackets, ornaments | visible `[U+XXXX]` placeholder |
| zero-width, bidi override, control characters | space (newline and tab kept) |
| very long strings, huge arrays, deep objects | bounded (`maxFieldChars`, default 2000; 2000 items; 500 keys; depth 12) |

`wrap(section, body)` takes a string or any JSON-able value; objects are cleaned
key and value, then serialised. `wrapText` is the whole-text variant for hosts
that assemble lines themselves.

## What it does not do

A fence lowers the odds that injected text steers the model. It does not make
the text safe. Keep the tools of an agent that reads outside text unable to do
harm (read-only, or a draft store a validator checks), set budgets, and treat
everything the model proposes to write as untrusted too.
