---
title: Provider chain and failover
description: An ordered list of pi-ai providers for a model. A classified failure continues the same call on the next one, mid-run included.
---

A model call can fail for reasons unrelated to the model: the account is out of
credits, the key was rotated, a rate limit, an outage, a regional refusal. A
**provider chain** is an ordered list of pi-ai providers. When a call fails in a
way another provider could fix, the same call (same messages, same tool results)
goes to the next provider. Nothing is lost: the conversation lives in the harness.

```ts
import { runAgent, createProviderChain } from "@droveragent/facade";

const providers = createProviderChain({
  providers: ["openrouter", "cloudflare-ai-gateway"], // pi-ai provider names, in order
  models: { "gpt-mini": "openai/gpt-4o-mini" }, // spec model name -> canonical id
});

const handle = runAgent(spec, input, { providers }); // spec.model = "gpt-mini"
for await (const e of handle.events) {
  if (e.kind === "provider_failover") console.log(e.from, "->", e.to, e.failureClass, e.status);
}
console.log((await handle.result).usageByProvider);
```

There is no adapter to learn. Each provider is pi-ai's own registry entry (base URL,
API, request quirks), the key comes from the resolver's env vars (`OPENROUTER_API_KEY`,
`CLOUDFLARE_API_KEY`), and the gateway's `{CLOUDFLARE_ACCOUNT_ID}` /
`{CLOUDFLARE_GATEWAY_ID}` come from `env`. The chain sees every model call of the
run: the main loop, subagents and the compaction summariser.

**Models outside the chain.** The chain routes a call whose model's provider is one of
its `providers`. A model that resolves to any other provider (a compaction
`summaryModel: "haiku"`, a subagent's own model) goes straight to pi-ai with the key the
resolver gave it: no failover, no `provider_failover` event, no response tap. So a cheaper
summary model on another provider keeps working; put its provider in the chain if it
should fail over too.

**What every provider receives.** A call's `onPayload` (the host's request-body patch) and
its request headers go to every provider the chain tries for that call, in order. Patch only
what all of them accept, or scope the patch inside `onPayload` by `model.provider`.

## Providers as settings

A provider can be a settings object instead of a name, so nothing has to live in process
environment variables: a Worker's secrets arrive as bindings, a multi-tenant host has one set of
credentials per tenant, a test sets everything explicitly.

```ts
// A Cloudflare Worker: secrets and ids from bindings, not process.env.
export default {
  async fetch(req: Request, env: Env) {
    const providers = createProviderChain({
      providers: [
        { name: "openrouter", apiKey: env.OPENROUTER_KEY, useEnv: false },
        {
          name: "cloudflare-ai-gateway",
          apiKey: env.CF_AIG_TOKEN,
          vars: {
            CLOUDFLARE_ACCOUNT_ID: env.CF_ACCOUNT_ID,
            CLOUDFLARE_GATEWAY_ID: env.CF_GATEWAY_ID,
          },
          headers: { "cf-aig-authorization": `Bearer ${env.CF_AIG_TOKEN}` },
          models: { "openai/gpt-5-mini": { id: "gpt-5-mini", contextWindow: 400_000 } },
          useEnv: false,
        },
      ],
      models: { "gpt-mini": "openai/gpt-5-mini" },
    });
    // ... runAgent(spec, input, { providers }) ...
  },
};
```

- `apiKey`, `baseUrl` (its `{PLACEHOLDER}`s filled from `vars`), `headers` (merged over the
  model's) and `models` are per entry. Anything absent falls back to `apiKeys`, `overrides`,
  `ids` / `extraModels` and then the environment; `useEnv: false` turns the environment off for
  that entry, so a missing setting makes the provider unusable instead of reading `process.env`.
- `models` puts a provider's model ids in one place: a provider id (`"b-mini"`), `null` (not served
  here), or a declaration for a model pi-ai's registry does not list (`{ id, contextWindow?, ... }`).
- Two chains with different credentials for the same provider run side by side in one process.
- Credentials and header values given here go to the provider and nowhere else: never into
  events, errors, the chain record, storage or traces (tested over a provider that echoes the key
  back in its error).

## Providers and models are data

- **Ids.** A canonical id is OpenRouter style. Per provider it defaults to the same
  id, except `cloudflare-ai-gateway`, which drops a leading `openai/` (pi-ai lists its
  OpenAI models unprefixed). Anything else is the `ids` table:
  `ids: { "openai/gpt-4o-mini": { "cloudflare-ai-gateway": "gpt-4o-mini" } }`; `null`
  means "this provider does not serve it".
- **Missing models.** A provider whose registry has no entry for the id is skipped
  (not a failure). The supported path is `extraModels`: a pi-ai `Model` object for
  that provider and id, checked before the registry, so no drover or pi-ai release is
  needed. A pi-ai bump that adds the entry later makes the `extraModels` entry
  redundant, not wrong.
- **Quirks.** A per-provider patch of the pi-ai model: `overrides: { "cloudflare-ai-gateway":
{ compat: { maxTokensField: "max_completion_tokens" } } }`.

## What fails over

Classification is **status first, structured fields only**. A class that can bench a
provider (credits, key, region) needs the HTTP status plus, where the class says so,
a field of the parsed error body. Message text is never searched for words: provider
errors echo request content (a rejected prompt, a page title), so text an outsider
controls could otherwise bench a provider. The fields come from the response tap (below).
Only when an attempt has no tap record are two things read from the text, because then
pi-ai keeps nothing else: the leading status code of the SDK's message (`"402 ..."`), and
on a 429 only, a "Retry-After: N" / "try again in Ns" hint (at most one wait of
`maxRateLimitWaitMs`, default 10 s).

| Class                | Needs                                                                       | Fails over          | Retried in place                                       | Skipped for the rest of the run |
| -------------------- | --------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------ | ------------------------------- |
| `credits_exhausted`  | 402; 403 + `limit_source: openrouter_key_limit`; 429 + `insufficient_quota` | yes                 | no                                                     | yes                             |
| `key_refused`        | 401; 403 + `code: invalid_api_key`                                          | yes                 | no                                                     | yes                             |
| `region_refused`     | 403 + `code: unsupported_country_region_territory`                          | yes                 | never                                                  | yes                             |
| `forbidden`          | any other 403 (no structured code)                                          | yes                 | no                                                     | **no**                          |
| `rate_limited`       | 429                                                                         | yes                 | once, if `Retry-After` is at most `maxRateLimitWaitMs` | no                              |
| `provider_error`     | 5xx                                                                         | yes                 | no                                                     | no                              |
| `timeout`            | 504, 408, the SDK's "Request timed out." / "Connection error."              | yes                 | no                                                     | no                              |
| `malformed_response` | an empty or truncated stream                                                | yes                 | no                                                     | no                              |
| `model_unavailable`  | 404                                                                         | yes                 | no                                                     | no                              |
| `invalid_request`    | 400, 413, 422                                                               | **no**              | no                                                     | no                              |
| `other`              | no usable status                                                            | yes, this call only | no                                                     | no                              |

`invalid_request` ends the chain by default: the same request would usually fail the same way
on the next provider. A model answer that fails the output schema is not a provider failure; the
chain never sees it. "Skipped" means tried last for later calls of the same run; it is
per run and per provider, nothing is shared.

### Choosing the action per class

The table above is the default. `actions` overrides it per failure class with one of:

| action   | what the chain does                                                                             | when it fits                                                                       |
| -------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `"stop"` | ends the call; no other provider is tried                                                       | a failure the next provider would repeat (the default for `invalid_request`)       |
| `"next"` | tries the next provider for this call only; this provider is asked first again on the next call | a failure specific to this provider and this call                                  |
| `"skip"` | tries the next provider and tries this one last for the rest of the run                         | a failure that will not heal within the run (the default for credits, key, region) |

The common case is a model alias or request field that only some providers accept: the first
provider answers `400 unknown model`, the second would have served the call. Set
`invalid_request` to `"next"`:

```ts
createProviderChain({
  providers: ["openrouter", "cloudflare-ai-gateway"],
  models: { "gpt-mini": "openai/gpt-4o-mini" },
  actions: { invalid_request: "next" },
});
```

The first provider is passed over for that call only and asked first again on the next one;
if every provider rejects the call, the run ends with each provider's class and status (no retry
loop: each provider is tried once per call). Keep the default when your providers accept the
same models and fields: a genuinely malformed request then fails fast instead of being sent to
every provider. A rate limit keeps its one in-place `Retry-After` wait under `"next"` and
`"skip"`.

A bare 403 is `forbidden`, not `key_refused`: over the plain transport a regional refusal,
a moderation refusal and a bad key all arrive as `403 <text>`, and only a structured field tells
them apart. It fails over, but the provider is asked again on the next call of the run.

If every provider fails, the call ends as an error carrying all failures:
`all providers failed: openrouter: credits_exhausted (402) | cloudflare-ai-gateway: key_refused (401)`
(status and code only; `includeProviderText: true` adds the providers' own text, which can quote
the prompt) and the same fields in the message's `diagnostics`. The run then ends `status: "error"`
with a `ProviderError` built from those diagnostics:
`provider error 401 (openrouter: credits_exhausted 402; cloudflare-ai-gateway: key_refused 401)`.

A stream that fails **after content was delivered** is not replayed on another provider (it would
duplicate output); the call ends as an error with the same class-and-status text and `diagnostics`
(never the provider's text unless `includeProviderText`). A failure before the first content event
is always eligible.

## Trace and usage

Every reaction is a `provider_failover` event (`retry` / `failover` / `exhausted`, from, to,
failureClass, status, code, waitMs): class and status, never provider text. On `failover` and
`exhausted`, `benched` says whether `from` is now skipped for the rest of the run (`true`) or was
only passed over for this call (`false`); the final error's `diagnostics` carry the same flag per
failure. `usage` events and `RunResult.usageByProvider` name the serving provider.
`usageByProvider` is cumulative over the run like `usage`: a resume or continuation restores it
from the checkpoint (for checkpoints written by this version; an older checkpoint has no split, so
it restarts from that invocation).

## Chain record

`RunResult.chainRecord` (and the `chain_record` trace event, emitted once before `run_end`) has
one entry per configured provider, in chain order, including providers that were tried and only
failed:

```ts
[
  {
    provider: "openrouter",
    answered: 0,
    failed: 1,
    failures: { key_refused: 1 },
    benchedAtTurn: 1,
    usage: { inputTokens: 0, outputTokens: 0 },
  },
  {
    provider: "cloudflare-ai-gateway",
    answered: 6,
    failed: 0,
    failures: {},
    benchedAtTurn: null,
    usage: { inputTokens: 5200, outputTokens: 610, costUsd: 0.004 },
  },
];
```

- `answered` counts calls the provider served; `failed` counts failed attempts (each in-place
  retry, failover or final failure), by class in `failures`.
- `benchedAtTurn` is the turn at which the chain first skipped the provider for the rest of an
  invocation (null if never).
- `usage` is the tokens and cost of the calls the provider served: the billed cost when the chain
  reports it (`billedCost`), pi-ai's list price otherwise.
- No provider text: classes, counts and numbers only.
- A resume or continuation of the run appends to the record of its previous invocation, read
  from the run's stored `chain_record` event (needs storage; without it a new invocation starts
  a fresh record).

## Structured provider errors

pi-ai flattens a failed call to the OpenAI SDK's text (`"403 <message>"`) and drops the response body
and headers (`onResponse` is not called for non-2xx). The chain restores them per attempt with a
**response tap**: it tags the attempt's request with a header, and one process-wide `fetch` wrapper
(installed once, pass-through for every untagged request, tag stripped before the request leaves the
process) reads a bounded copy of a non-2xx body and records the status, a header allow-list
(`retry-after`, `retry-after-ms`, `x-ratelimit-*`, `x-request-id`, `cf-ray`; nothing else) and the parsed
error fields (`error.code`, `limit_source`). Classification uses those fields first (message text is only a fallback: the SDK's leading status when the tap is off, and a `Retry-After` hint on a 429 without the header, always capped by `maxRateLimitWaitMs`), so a
region refusal is `region_refused` and a real `Retry-After` header is honoured. The failure's status, code,
`retryAfterMs` and kept headers are on the final message's `diagnostics`; events and the default message
carry status and code only, and `includeProviderText: true` opts in to the providers' own text.

Attempt tags are random UUIDs and a response is recorded only for a live attempt. The error
body is read up to 16 KB (counted in bytes; one large chunk is sliced, so a 5 MB body costs
16 KB). Kept header values are cut to 128 characters and must be plain (`A-Z a-z 0-9` and
`._:,=/ -`); any other value is dropped, so a provider cannot smuggle markup or request text
through a header into the diagnostics. `Retry-After` is read strictly (seconds or an HTTP date);
a value above `maxRateLimitWaitMs` or a malformed one is not waited on and the chain fails over.

The tap patches `globalThis.fetch` once per process and tags an attempt only while the global is
still the tap. It switches itself off (no tag header is sent; classification falls back to the
SDK's leading status) when:

- `fetch` cannot be patched: a frozen or non-writable global. On Cloudflare Workers `fetch` is
  normally an ordinary writable global, so the tap works there too; the off switch covers
  runtimes or hosts that lock it down.
- something replaces `globalThis.fetch` after the tap installed (another wrapper, a test double).
- two copies of `@droveragent/model` are installed (for example two versions in one bundle): each
  copy patches `fetch`, the second wraps the first, and the first copy's tap turns itself off, so
  chains created from that copy classify from the status only. Deduplicate the package to keep
  structured errors everywhere.

The tap needs the OpenAI SDK to resolve `globalThis.fetch` when its client is created (true for the version
pi-ai uses); a `streams` entry (custom transport) is not tapped and supplies its own `status` / `error: { code }`
on a thrown error. Without a tap record the chain falls back to the SDK's leading status.

## Billed cost

pi-ai prices every call from the model's list rates and drops the cost the provider
reports. OpenRouter reports the amount actually billed (`usage.cost`, with routing,
discounts and cache pricing folded in) when the request asks for it. With
`billedCost: true` the chain asks OpenRouter for it and, through the same response tap,
reads it from the response and makes it the call's cost:

```ts
const providers = createProviderChain({
  providers: ["openrouter", "cloudflare-ai-gateway"],
  models: { "gpt-mini": "openai/gpt-4o-mini" },
  billedCost: true,
});
```

- The billed figure **replaces** pi-ai's list-price total for that call; it is never
  added to it, so nothing is counted twice. The per-component fields stay list-price.
- Only OpenRouter requests change (by provider name, or a base URL on `openrouter.ai`).
  Other providers (the gateway included) get no body key and keep pi-ai's list price, so
  `usageByProvider` mixes billed and list-price figures by provider, and `usage.costUsd`
  is their sum.
- `quota.maxCostUsd` (and a continuation's own `budget.maxCostUsd`, where that lands) runs
  on the same per-call figures.
- Without a chain, wrap the transport instead: `runAgent(spec, input, { streamFn:
  withProviderCost() })`. A chain does not use `streamFn`, so under a chain use
  `billedCost`.

## Limits

- Without a tap record (a custom `streams` entry, or a runtime where `fetch` cannot be patched) only the
  SDK's leading status survives: a region refusal is then a bare 403, classed `forbidden` (it fails over,
  is not retried in place and is not benched).
- A caller abort is a cancel even when the transport reports it as an error ("Connection
  error."): the call ends `aborted`, nothing is classified, nothing fails over.
- The OpenAI client's own retries are off (`maxRetries: 0`): failing over is the retry.
- Usage of failed attempts is not counted, except the last one. An attempt that fails before
  its first content event is dropped with its usage (even if the provider billed it) and the
  call moves on; only the attempt that ends the call (its answer, a failure after content, or
  the final failure when every provider failed) reaches `usage` and `usageByProvider`. A
  failure after content keeps pi-ai's list-price usage, not a billed figure (no billed figure
  arrives without a final usage chunk).
- Not verified against live OpenRouter or Cloudflare endpoints: tests use local servers.
