---
title: Evals
description: How drover's eval suite is structured and how to add scenarios.
---

drover ships an eval suite at the repo root (`evals/`) plus a Vite-based
viewer (`apps/eval-viewer/`). The suite is intentionally simple — a flat
list of `Scenario` records plus a runner — so you can read and copy it.

## Run the suite

```bash
cd evals && bun run.ts
```

Runs every scenario against OpenRouter using the model aliases in
`@droveragent/model`. Results land in `evals/eval-results/<timestamp>/`.

Filter:

```bash
bun run.ts write-article fix-code-bug
```

## Scenario shape

```ts
import type { Scenario } from "./scenarios/types.ts";
import { defineAgent } from "@droveragent/core";
import { Type } from "@sinclair/typebox";

const spec = defineAgent({
  id: "summariser",
  systemPrompt: "...",
  inputSchema: Type.Object({ file: Type.String() }),
  outputSchema: Type.Object({ summary: Type.String() }),
  model: "cheap",
  tools: ["read"],
  quota: { maxTurns: 4 },
});

export const scenario: Scenario<typeof spec> = {
  id: "summarize-doc",
  name: "Summarise an incident report",
  inspiredBy: "generic",
  description: "Read a doc and produce a 3-bullet summary.",
  fixtureDir: "summarize-doc", // optional: evals/fixtures/<name>/
  spec,
  input: { file: "incident.md" },
};
```

Add to `scenarios/index.ts` exports. The runner picks it up.

## Fixtures

If `fixtureDir` is set, the runner snapshots `evals/fixtures/<name>/`
into `eval-results/<timestamp>/<scenario>/workdir/` before the run. The
agent's `cwd` is the workdir copy — runs don't mutate the canonical
fixture.

## Plugin observability per scenario

The runner attaches `stepTracerPlugin()` to every scenario via
`options.plugins`. After the run, the recorded steps land in
`result.json.trace`.

If your scenario needs additional plugins (e.g. `phaseRecorderPlugin`),
attach via `spec.plugins`. The runner's tracer is additive.

## Skills

If the spec declares `skills` and the fixture has a `skills/` dir, the
runner auto-scans + builds a registry per run. See
[Skills](/guides/skills) for the layout.

## MCP

When any scenario in the run set declares `mcpServers`, the runner lazy-
boots an MCP runtime with the configured fixtures (currently the in-repo
stdio server at `evals/fixtures/mcp-stdio/server.ts`). See [MCP](/guides/mcp).

## Runtime-queue scenario

`runtime-queue` exercises `@droveragent/runtime` end-to-end: enqueue 5 echo
jobs with `concurrency: 3`, wait for terminal status on each, assert
`done`. Uses an in-memory queue + in-memory storage so it's hermetic.

## Viewer

```bash
cd apps/eval-viewer && bun run dev
```

Hash-routed pages:

- `/` — every runset with chip-grid jumpoffs to scenarios
- `#/r/<runset>` — runset table
- `#/r/<runset>/<scenario>` — full scenario detail with timeline
- `#/storage` (if `DROVER_STORAGE_URL` set) — runs from libsql storage

The timeline component renders the full event stream: assistant text in
markdown, thinking blocks collapsed by default, tool cards expanding to
show input + result.

## Record and replay provider responses

`@droveragent/eval` records a run's model responses and replays them offline (no network,
no cost) through the harness's `streamFn` seam (`HarnessDeps.streamFn`):

```ts
import { Effect } from "effect";
import { runAgentEffect } from "@droveragent/harness";
import { createRecorder, recordStream, replayStream } from "@droveragent/eval";
import { streamSimple } from "@earendil-works/pi-ai/compat";

const rec = createRecorder();
await Effect.runPromise(
  runAgentEffect({
    spec,
    input,
    ctx,
    emit,
    deps: { ...deps, streamFn: recordStream(streamSimple, rec.sink) },
  }),
);
await Bun.write("run.json", JSON.stringify(rec.recording()));

// later, in CI (no network):
const recording = JSON.parse(await Bun.file("run.json").text());
const result = await Effect.runPromise(
  runAgentEffect({ spec, input, ctx, emit, deps: { ...deps, streamFn: replayStream(recording) } }),
);
```

Make one `recordStream` / `replayStream` per run; subagents share it.

**Keying.** Turns are keyed by conversation, not by global call order. A conversation
(`thread`) is the system prompt plus the first message, so each agent run, and each
subagent, has its own; `threadIndex` counts calls within it. Replay serves the first
unused turn of the call's thread whose request hash matches. Parallel subagents whose
calls interleave differently from the recording replay correctly.

One case cannot be told apart: two subagents with an identical system prompt AND first
message that ran at the same time share a thread. When a replayed call matches two such
recorded turns with different answers, replay fails with `ReplayAmbiguousError` instead of
handing one subagent the other's answer; give each concurrent subagent a distinguishing first
message (a task id) and record again. A sequential repeat of the same request (a retry) is
not ambiguous: it is served in recorded order.

**Drift.** Each turn stores a hash of its request (system prompt, messages, tool names;
`timestamp` and `durationMs` fields excluded). With pi 1.x the system prompt and the tool
declarations live in the transcript's leading system message, so that is where the hash
reads them from. A request that matches no recorded turn fails the call with
`ReplayDriftError`, naming the call (`replay drift at call 1 of thread 3f... (recorded turn
1)`), so a changed prompt or tool result fails loudly. `onDrift: "ignore"` or a callback
replays the thread's next turn anyway (or, for an unknown thread, the next turn in recording
order). More calls than recorded: `ReplayExhaustedError`. The hashes are a 53-bit change
detector, not an integrity check: never use them to authenticate a recording.

**Format version.** `RECORDING_VERSION` is `2`. Version 1 recordings were keyed on the
pre-pi-1.x request shape and cannot match any request made now, so `replayStream` rejects
them with an error telling you to re-record.

**Determinism.** Replay returns the recorded events verbatim (deep copies): content,
tool-call ids and usage are the recorded ones, so events and output match the recorded run
except wall-clock fields (`ts`, `durationMs`).

**What is stored.** The request hash and the response events. API keys and request headers
are never recorded. A failed call's raw provider text (`errorMessage`, which can quote the
prompt) is replaced by its status-only form (`provider error 402`) unless
`recordStream(real, sink, { keepProviderText: true })`; the live run is unaffected.

**Recording failures.** A `sink` or `redact` that throws or rejects never hangs or fails the
live run: the call's terminal event is always delivered, and that turn is left out of the
recording. The failure goes to `onError` if given, else onto the returned function's `errors`
list; check it after the run, since a recording with errors is incomplete:

```ts
const streamFn = recordStream(streamSimple, rec.sink);
// ... run ...
if (streamFn.errors.length > 0) throw new Error("recording incomplete");
```

**Redaction.** `redact` gets a deep copy of each turn and returns the turn to store. Change the
response events only: keep `index`, `thread`, `threadIndex` and `requestHash` as they are,
since replay matches on them.

<Warning>
  A recording contains the full model responses and, through tool results echoed in them, whatever
  private data the run touched. Do not commit recordings of private data. Record against synthetic
  data, or scrub with `recordStream(real, sink, {redact})`.
</Warning>

## A fake provider with failures

`fakeProvider(script)` is a `streamFn` that answers each model call with the next scripted
step, including the failures real providers produce. No network. `calls` records every
request it received.

```ts
import { fakeProvider, faults, reply } from "@droveragent/eval";

const fake = fakeProvider([
  reply.toolCall("read", { path: "a.md" }),
  faults.credits(), // 402
  reply.text("done"),
]);
```

| Step                                              | What the run sees                                                           |
| ------------------------------------------------- | --------------------------------------------------------------------------- |
| `faults.credits()`                                | 402: `ProviderError`, `provider error 402`                                  |
| `faults.forbidden({ region? })`                   | 403 (a region refusal with `region: true, structured: true`)                |
| `faults.rateLimited(seconds)`                     | 429 with `Retry-After` (exact seconds, e.g. `0.5`; same wait in both modes) |
| `faults.serverError(status = 503)`                | a 5xx                                                                       |
| `faults.timeout()`                                | the SDK's "Request timed out." (no status)                                  |
| `faults.empty()`                                  | a completion with no content and zero usage                                 |
| `reply.text(text)` / `reply.toolCall(name, args)` | a normal answer; tool-call ids are `call_<n>`                               |

Failures are pi-shaped by default: an `error` event with `errorMessage` `"<status>: <text>"`,
the shape pi-ai 1.x produces over the real transport. `structured: true` throws an error
carrying `status`, `error.code` and `retryAfterMs` instead: that is what a provider chain
reads from a custom transport (a region refusal is then `region_refused`), but outside a
chain a thrown error fails the loop, so use it only as a chain `streams` entry.

## With a provider chain

A provider chain does not use `streamFn` (see the [provider chain guide](/guides/provider-chain)).
Record, replay or fake each provider through the chain's `streams` option instead:

```ts
const providers = createProviderChain({
  providers: ["openrouter", "cloudflare-ai-gateway"],
  models: { "gpt-mini": "openai/gpt-4o-mini" },
  streams: {
    openrouter: fakeProvider([faults.credits()]).streamFn,
    "cloudflare-ai-gateway": fakeProvider([reply.text("ok")]).streamFn,
  },
});
```

A `streams` entry never goes through `fetch`, so the chain's response tap (structured errors,
billed cost) does not see it: a recorded or faked call carries only what the step itself
provides (pi's flattened text, or the `structured` fields).
