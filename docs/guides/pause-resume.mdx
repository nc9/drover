---
title: Pause / resume
description: Suspend a run, persist it, continue later. Across processes.
---

drover supports durable pause and resume. The harness checkpoints the
pi-agent-core message list at every turn boundary; calling `pause()`
flips the run's status to `paused` and `resumeAgent` picks up from the
saved messages. With [compaction](/guides/compaction) enabled the
checkpoint stores the _compacted_ history, so resume replays the
shortened transcript rather than re-deriving it.

## Prerequisites

Storage must be wired. Without it, `pause()` degrades to plain `abort()`
and the run is marked `cancelled` — there's no checkpoint to resume
from.

```ts
import { createLibsqlStorage } from "@droveragent/storage";

const storage = await createLibsqlStorage({ url: "file:./var/runs.db" });
```

## Pause

```ts
const handle = runAgent(spec, input, { storage });

(async () => {
  for await (const e of handle.events) {
    if (e.kind === "usage" && /* some condition */ true) {
      handle.pause(); // flips pauseFlag, aborts the inner loop
    }
  }
})();

const result = await handle.result;
console.log(result.status); // "paused"
console.log(result.runId); // record this for the resume call
```

## Resume

```ts
import { resumeAgent } from "@droveragent/facade";

const handle = resumeAgent(spec, runId, { storage });
const result = await handle.result;
console.log(result.status); // "success" / "error" / re-paused
```

`resumeAgent` checks four things before replaying:

1. **Run exists** in storage.
2. **Status is `paused`** (or `success` with `appendMessages`, see
   below). A `running` run is refused; error/quota/cancelled runs would
   duplicate tool side effects.
3. **Agent id matches** `spec.id`.
4. **Spec hash matches** `runRow.specHash`.

Any failure returns `RunResult.error.tag === "ResumeError"`. The Promise
never rejects.

## Continue a finished run with new input

A run that ended `success` can be carried on when new input arrives: a new
document for the same case, a follow-up question. `appendMessages` adds user
turns to the stored history (the final checkpoint of a successful run holds
the complete conversation, last answer and tool results included) and the
loop runs again under the same `runId`.

```ts
import { resumeAgent } from "@droveragent/facade";

// Earlier: const first = await runAgent(spec, { site }, { storage }).result;

async function onNewInput(runId: string, text: string) {
  const result = await resumeAgent(spec, runId, {
    storage,
    plugins: [fence], // the same untrustedResultsPlugin the run started with
    // Outside text: fenced by the run's fence before it enters the history.
    appendMessages: [{ content: text, untrusted: true }],
    // This continuation's own allowance, counted from here:
    budget: { maxTurns: 8, maxTokens: 200_000, maxCostUsd: 0.5, maxDurationMs: 120_000 },
  }).result;

  if (result.status === "quota") console.warn(result.error?.message); // "invocation tokens budget exceeded (...)"
  console.log(result.finalText);
  console.log(result.usageDelta); // this continuation only
  console.log(result.usage); // the whole run so far
  return result;
}
```

- Without `appendMessages` only `paused` runs resume; with it, `success`
  runs can be continued too. `error`, `quota` and `cancelled` runs are refused.
- `budget` is per invocation: turns, tokens (input + output + cache), USD and
  wall-clock ms counted from where this call starts. The spec's `quota` still
  applies too, but only its turns and cost are cumulative over the whole run:
  `quota.maxDurationMs` restarts with every invocation (resume or
  continuation). The first breach wins and ends the call `status: "quota"`.
  Exception, as for `quota`: a validated final answer wins over a breach of
  its own call. For `budget.maxTurns` that holds always. For `budget.maxTokens`
  and `budget.maxCostUsd` it holds only once the spec's `quota.wrapUp`
  warning fired (`budget` has no warning of its own); see
  [the answer wins over its own breach](/concepts/agent-spec).
- A continuation of a run already past the spec's `quota.wrapUp` threshold
  carries the budget notice from its first call. The notice is per call and is
  never stored in the checkpoint.
- `usage` and `usageByProvider` are cumulative over the run (both are stored in
  the checkpoint); `usageDelta` is this call only.
- `appendMessages` content is untrusted when it comes from outside your
  system: it goes into the history as a user turn and can carry prompt
  injection. Pass such an item as `{ content, untrusted: true }`: the run's
  fencing plugins (`untrustedResultsPlugin`, or any plugin with
  `wrapUntrusted`) fence it, section `"appended-input"`, after their
  `assertResumable` check passed, so a resume whose fence nonce is lost is
  refused before anything is appended. A plain string, or an item without
  `untrusted: true`, goes in as written. With **no** fencing plugin on the run
  an untrusted item also goes in as written: the flag only fences when a fence
  is configured. The run then emits one `warning` event (`code:
  "untrusted_unfenced"`, `count`) right after `run_start`, so the host can see
  it. A fence that throws ends the call `PluginError` naming that plugin;
  nothing is appended or stored (the run row, checkpoint and events stay as
  they were). See [Untrusted data](/guides/untrusted-data).
- Continuations are **not serialised across processes**. A run whose status is
  `running` is refused, but that check is not atomic: two continuations of one
  `runId` started at the same moment can both pass it and then run interleaved.
  That **corrupts the stored run**: their events interleave under one run id
  with clashing seqs, the checkpoints mix two histories, one message set is
  lost, and tool side effects may run twice. The host must serialise
  continuations per `runId`, for example by running each one as a job on
  `@droveragent/runtime`'s `QueueAdapter` (its job lease gives one holder at a
  time and `reclaimStale` recovers a crashed one), or with a lock or a DB
  advisory lock. A storage-level lease is a pending decision (#21).
- A process that crashes mid-run leaves the run row `running`; resuming it is
  refused until the host resets the status (once sure nothing is running it).
  Reclaiming a crashed holder automatically is part of the same lease work.

## Spec drift

`hashSpec(spec)` covers everything that affects replay:

- `id`, `tools`, `skills`, `mcpServers`
- `model`, `systemPrompt` (function-valued prompts hash via `.toString()`)
- `inputSchema`, `outputSchema`
- `subagents`, `outputRetries`, `quota`
- `memory`, `instructionFiles`, `promptTemplate`, `lifecycle`, `compaction`
- `plugins` (by id — bump the plugin id when its behaviour changes)

If you edit the system prompt and resume, drover rejects with:

```
spec drift on agent "<id>": recorded hash <a>, current hash <b>.
The agent definition changed since the run was paused — resuming
would replay old messages under a different policy.
```

Migration: write a new run row explicitly rather than mutating the spec.

## Cross-process resume

The run row + checkpoint live in libsql. Any process pointed at the same
DB can resume — the eval runner pauses, a long-running daemon resumes.

```ts
// process A
const storage = await createLibsqlStorage({ url: "libsql://..." });
const handle = runAgent(spec, input, { storage });
// ... pause ...

// process B (different machine even)
const storage = await createLibsqlStorage({ url: "libsql://..." });
const handle = resumeAgent(spec, runId, { storage });
```

## Pause / resume with the runtime layer

When you're using `@droveragent/runtime`:

```ts
const api = createRunApi({ queue, storage, registry, sandboxFor });

// Worker pool pauses a job by signalling cancel + the agent calling pause().
// The queue row stays "done" (it completed once); the run row stays "paused".

// Later, drive the resume:
const result = await api.resume(jobId);
```

`api.resume` does the validation, calls `resumeAgent` inline, and
reflects the final status back into the queue.
