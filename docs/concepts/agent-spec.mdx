---
title: AgentSpec
description: The serialisable substrate every agent reduces to.
---

```ts
interface AgentSpec<ISchema = TSchema, OSchema = TSchema> {
  id: string;
  systemPrompt: string | (ctx: RunContext) => string | Promise<string>;
  inputSchema: ISchema;
  outputSchema: OSchema;
  model: ModelSpec;
  tools: readonly string[];
  skills?: readonly string[];
  mcpServers?: readonly string[];
  subagents?: SubagentConfig;
  outputRetries?: number;     // default 2
  plugins?: readonly HarnessPlugin[];
  quota?: RunQuota;           // { maxTurns?, maxDurationMs?, maxCostUsd?, maxTokens?, wrapUp? }
}
```

JSON-serialisable except for `systemPrompt` (when fn) and `plugins`
(functions). Dynamic agents (LLM-composed at runtime) build the same
shape — drover doesn't distinguish.

## `ModelSpec`

```ts
type ModelSpec =
  | string // "cheap" | "google/gemini-2.5-flash-lite" | "sonnet:high"
  | { name: string; reasoning?: ReasoningLevel; temperature?: number; maxTokens?: number };
```

Lookup order: alias map (`@droveragent/model`'s `DEFAULT_ALIASES` plus per-
call overrides) → provider-prefixed slug `provider:modelId` → pi-ai
builtin model id (searched across every registered provider).

Slug form: `"<name>:<reasoning>"` parses cleanly. Reasoning levels:
`minimal | low | medium | high | xhigh`. Models with `reasoning: true`
in pi-ai's registry default to `"medium"` if you don't pick.

## `SubagentConfig`

```ts
interface SubagentConfig {
  allowed: readonly string[]; // required
  depth?: number; // default 2
  fanOut?: number; // default 3

```

## Identity builder

`defineAgent(spec) → spec` returns the input unchanged. The builder
exists for type inference: `AgentInput<S>` and `AgentOutput<S>` derive
their static types from the spec's TypeBox schemas.

```ts
const spec = defineAgent({
  /* ... */
});
type In = AgentInput<typeof spec>;
type Out = AgentOutput<typeof spec>;
```

## Spec hash

`hashSpec(spec)` covers every field that affects execution:
id / tools / skills / mcpServers / model / systemPrompt /
inputSchema / outputSchema / subagents / outputRetries / quota /
plugins (by id).

Plugin function bodies aren't included — bump the plugin's `id` when
its behaviour changes. Function-valued `systemPrompt` uses
`Function.toString()` so source edits produce different hashes (but
closure-over-variables drift is invisible — prefer string prompts on
resumable agents).

## Finishing inside a budget

A hard budget (`maxTurns`, `maxTokens`, `maxCostUsd`, `maxDurationMs`) ends the run with
`status: "quota"` and no answer. `maxTokens` counts every token the provider reports
(input, output, cache read, cache write), summed over calls. Input is per call and each call
resends the conversation so far, so input tokens grow with every turn: a 10-turn run whose
history reaches 8 000 tokens spends far more than 8 000 input tokens. Add `quota.wrapUp` to let
the model finish cleanly first:

```ts
quota: { maxTurns: 12, maxTokens: 200_000, maxCostUsd: 0.5, wrapUp: { at: 0.8 } }
```

Once any budget is `at` spent (default 0.8), every following model call carries a closing user
message: the budget is nearly spent, do not call more tools, answer with what you have. For
turns, the notice starts on the turn about to begin whose number (1-based) is
`min(ceil(at × maxTurns), maxTurns - 1)`, and on turn 1 if that is below 1: so it arrives no later
than the second-to-last allowed turn, leaving at least one turn to answer in. With `maxTurns: 1`
the first and only call already carries it (and an answer on that turn still counts, see below). A `budget_warning` event (`dimension`, `limit`, `used`)
is emitted once. `wrapUp.message` replaces the default text.

- **Outcome.** `RunResult.wrapUp` (`dimension`, `limit`, `used`, `outcome?`, `overshoot?`) is
  set whenever the warning fired: `outcome: "wrapped_up"` for `status: "success"`,
  `"cut_off"` for `status: "quota"`, and no `outcome` for a paused, cancelled or errored run.
- **Bounded.** The wrap-up turns run inside the same hard limits: a model that ignores the
  notice, or keeps calling tools, is cut off as before (`cut_off`). Set `at` low enough that
  one more call fits in the remainder.
- **The answer wins over its own breach.** If the run's final answer (the call that ends the
  run, with no tool call) passes the output contract, it wins over a budget breach caused by
  that same call: the run is `success` (with `outcome: "wrapped_up"` once the warning fired).
  - `maxTurns`, for every run: reaching the cap on the answer turn is not a breach (that turn
    was allowed; `maxTurns` is a budget, not a tripwire) and records no overshoot.
  - `maxTokens` and `maxCostUsd`, only once the wrap-up warning fired: this is an overshoot and
    `wrapUp.overshoot` (`dimension`, `limit`, `observed`, `scope`: `"spec"` or `"budget"`) records the excess. Without
    `quota.wrapUp` a cost or token breach ends the run `quota`.
  - A per-invocation `budget` (resume or continuation, see
    [pause and resume](/guides/pause-resume)) follows the same rule. Its turn cap is never an
    overshoot on the answer turn; its token or cost cap is forgiven only once the SPEC's
    `quota.wrapUp` warning fired in this invocation. `budget` has no wrap-up warning of its
    own, so without `quota.wrapUp` (or before its threshold) a `budget` breach ends `quota`.
  - If that call failed at the provider (`stopReason: "error"`), the provider error is the
    outcome: the run ends `error` with `ProviderError`, not `quota` / `cut_off`, for a turn
    breach and, once the warning fired, a cost or token breach.

  The `postSuccess` lifecycle is skipped in both cases (the budget is spent). An answer that
  fails the output schema, or a breaching call that asked for tools, still ends `quota`; a
  wall-clock breach always does.

- **Output schema.** The wrap-up answer is decoded and validated like any other; output
  retries still apply and still count against the budgets.
- **Operator text.** The notice is the spec's `wrapUp.message` or the built-in default, never
  built from tool output. It is harness text added as a user turn and is not fenced as
  untrusted data (the untrusted-data fence is separate work).
- **Post-processing.** The notice is not added to the `postSuccess` lifecycle's calls.
- **History.** The notice is appended per call, never written to the history or the
  checkpoint, so a resumed run recomputes it (against the run's cumulative turns, tokens and
  cost; wall clock is measured per invocation) and may warn again.
- **Subagents** have their own spec and quota: a parent's notice is not passed to a child,
  and a child's `wrapUp` applies to the child's run only.
- **Continuations.** A per-continuation budget (resume with its own budget, a separate change)
  does not trigger the notice yet; `wrapUp` follows the spec's cumulative `quota`.
- **Testing.** `HarnessDeps.now` replaces the clock used for the wall-clock threshold.
